# rmt-gatekeeper · 从热点里筛出"值得写的那一条"

> 把"哪条热点值得跟"这件事，从**凭经验判断**变成**可执行、可检验、可迭代的七道闸门**。
> 其中三道落成了工具，**用 16 个真实判断错误做了全量验证**。
>
> 作者：YEJILIZ

| | |
|---|---|
| 规模 | 判据文档 8 份 ｜ 工具代码 7 个文件 ｜ 单元测试 **164 项** |
| 验证样本 | **53 篇**历史稿全量读稿 ｜ **16 个**真实判断错误 ｜ **50 条**当日榜单实测 |
| 核心结果 | 可自动判定的 **6 条全部命中（6/6）**；其余 10 条经逐条核对**全属必须人判**的闸门 |

## 一、问题

我在做一份日常的信息报送工作：**每天从微博榜单里挑值得跟的热点，核到源头，写成报送件**。
干了两个月，攒下一份"被否掉的选题台账"，翻回去看，犯的错高度重复：

- **旧闻新炒**：榜单上"新出"的词条，点开一看是四个月前的旧事（**犯了三次**）
- **媒体报了，网民没说话**：稿子写完才发现话题页最新帖停在两个月前
- **讨论量个位数**：写出来即失真
- **论据全来自媒体转述**：话题页里确实有真人，但我引用的证据链里一条网民原话都没有

**这些问题有共同点：全部可以在动笔之前发现，而我全部是写完之后才发现的。**

于是我把判据反向提炼成一道**七闸门决策树**（议题真实／时效窗口／议论够量／性质匹配／事实有源／落点接口／特别处置），
再问一个工程问题：**这七道闸门里，哪些能交给代码，哪些必须留给人？**

答案决定了整个项目的形态：

| 闸门 | 可自动化 | 理由 |
|---|---|---|
| 2 时效窗口 | **可自动** | 纯日期计算 |
| 3 议论够量 | **可自动** | 阈值判定 |
| 3-② 发帖人构成 | **可自动** | 页面标识可判 |
| 1-② 证据链 | **可自动** | 纯读稿、不联网 |
| 1-① 议题真实 | 半自动 | "是不是博主解读"需人判 |
| 4 性质匹配 | 半自动 | 体裁定性需人判 |
| 5 事实有源 | 半自动 | "够不够权威"需人判 |
| **6 落点接口** | **人判** | 问的是"**领导能下令干什么**" |
| **7 特别处置** | **人判** | 问的是"**要不要报**"——政治判断 |

## 二、方案

### 三道闸门落成工具

```
node tools/yuqing/scrape.cjs   <候选清单.json> --prefilter      # 榜面粗筛 → 生成取数脚本
node tools/yuqing/judge.cjs    <候选清单.json> <取数结果.json>   # 出判定报告
node tools/yuqing/judge.cjs    --audit-sources                 # 闸门 1-②：读稿体检（不联网）
node tools/yuqing/mk_eval_frozen16.cjs                         # 历史复核（用冻结数据）
```

| 模块 | 职责 |
|---|---|
| `lib.cjs` | **纯逻辑层**（无网络、无 IO）——所有判据、阈值、时间计算都在这 |
| `page_scrape.gen.cjs` | 浏览器侧**代码生成器** |
| `scrape.cjs` | 取数入口：榜面粗筛 ＋ 生成脚本 |
| `judge.cjs` | 判定层：结论表 ＋ JSON ＋ 可读报告 |
| `test_lib.cjs` | **单元测试 164 项** |
| `check_generated.cjs` | 静态自检（语法／转义／**两份分类规则一致性对账**） |

### 判定报告的输出形态

```
## 一、结论一览          一张表：词条／型／事情时效／议论时效／议论量／结论／依据
## 二、逐条明细          每条一节：闸门 2 依据、闸门 3 依据、发帖人构成、失败项
## 三、没被判的闸门       ★明写哪些必须人判★
```

**第三节是这份报告最该看的地方——它告诉你工具在哪儿停下来。**

### 三个自己长出来的方法

**① 时效必须拆成两条独立检查。**

原来只有一条"时效"。实测发现必须拆：

| 事情 | 议论 | 性质 | 处置 |
|---|---|---|---|
| 旧 | 旧 | 旧闻新炒 | pass |
| 新 | 旧 | **网民没反应** | pass |
| **旧** | **新** | **旧案翻红** | **可写（勿误杀）** |
| 新 | 新 | 时效成立 | 看议论量 |

不拆就会犯**两种相反的错误**：把"旧案翻红"误杀（损失好选题），或把"媒体报了但网民没反应"当成热舆情（白写一篇）。

**② 榜单词条型用替代判据，而不是"取不到数据就放弃"。**

有些榜单词条没有独立话题页、读不到讨论量。**"抓不到数据"与"议论没形成"是两回事**——
改用三个替代指标：榜单热度值／在榜位次／24h 内新帖占比。实测这一档单独拦对了历史错误。

**③ 发帖人构成：帖子新鲜 ≠ 网民在议论。**

某个话题页 24 小时内有十几条新帖，**但发帖的全是媒体蓝 V**——媒体在替网民说话。
新增判据：24h 新帖中普通用户占比 ≥30% **且** 达人/机构占比 <50%。

> 这一档上线后第一次真实运行就打中一条历史错误稿：**13 条帖子里 12 条是媒体**，
> 而该稿的历史问题正是"来源表里没有网民个人账号"——**工具从完全不同的角度独立打中了同一条**。

## 三、权衡

**① 为什么不做全自动。**

第六道闸门问的是"**领导拿到这条能下令干什么**"，第七道问的是"**要不要报**"——**都是政治判断，不能交给模型**。

这条不是姿态，是实测出来的：

> 有一条历史选题 **1.1 万讨论／4995 万阅读（当日全场最高）**，闸门 2、3 会**必然放行**它。
> 但它的毛病不在量或时效——**在于区级没有接口**（决定权在国家／省级）。
> **这条正好证明了为什么第六道闸门不能自动化。**

所以工具的设计目标不是"替人决定"，而是**把便宜、可重复的判断前置，把昂贵的判断留给人**。

**② 为什么复核历史问题必须用"冻结数据"。**

历史判决要配历史数据。同一个词条的讨论量今天已涨到当时的十倍；
拿今天的数字去评价当时的判断，等于**用今年的天气评价去年的出行决定**。

所以全量验证一律用文献里写死的**当时值**，每条带出处。

**③ 为什么取数不并发。**

浏览器 worker 之间**共享同一个页面对象**，并发会互相踩：A 跳转之后 B 又跳走，A 再取页面就是 B 的。
曾用并发 3 跑 4 条候选，**其中 3 条数据全部串成了同一条**。→ 改串行。

**④ 为什么"查不到"不能当成"判定结果"。**

实测踩过：用简称查词条 → 两个入口全空 → 被报成"议论不足 → 否决"。
**"查不到"和"议论没形成"是两件事**，现在分开报：`词条名对不上（未判定）` / `数据不足（未判定）` / `取数异常`。

## 四、结果

### 16 个真实判断错误的全量验证

| 归属 | 条数 | 判定器表现 |
|---|---|---|
| 闸门 2（时效） | 2 | **2/2 拦住** |
| 闸门 3（议论量） | 1 | **1/1 拦住** |
| 闸门 1-②（证据链） | 3 | **3/3 拦住** |
| **小计：可自动判定** | **6** | **★6/6★** |
| 闸门 4/5/6/7 与 1-① | 10 | **按设计必须人判**，逐条列明归属 |
| 数据源不属微博（本地留言板） | 1 | **显式排除**，不硬算进分母 |

**这个数字的价值不在 "6/6"，在于它经得起追问：**

- 为什么只有 6 条？——因为另外 10 条是政治判断，**工具不该碰**。
- 那 10 条怎么保证不误判？——**不保证，所以它们是"先问，不自决"**。

### 53 篇历史稿的全量读稿（闸门 1-②）

```
共 53 篇｜过 42 篇｜✗ 来源列内无网民个人账号 11 篇
```

其中包含全部 3 条被反向验证点名"原判据拦不住"的稿子。

### 50 条当日榜单的实跑

```
社会榜全 50 条（逐条从榜单原链抓取）
→ 判定：✓ 可写 17｜✓ 可写（须报薄）13｜✗ 否决 20
```

粗筛这一层是实测逼出来的：**该写的条目里 4/5 热度不到 100 万**，
所以尺子用**位次＋议题族去重**（同一事件在榜上常有 2—8 条），而不是热度值。

> 另一轮 19 条的实跑里，**7 条被"发帖人构成"判据拦住**（媒体／博主主导），
> 说明这一档在真实数据上是常态触发、不是摆设。

### 工程上的自我约束

| 做法 | 为什么 |
|---|---|
| 判定逻辑与取数分离 | `lib.cjs` 无网络无 IO，**164 项单元测试全部不联网** |
| 每个结论带 `gate` / 依据 / 数据出处 | 判定必须可溯源，否则没法复盘 |
| 生成器另配静态自检 | 两份分类规则用**故障注入验证过**能抓到不一致 |
| "查不到"分三种结果 | 不许把工具故障伪装成判定结论 |
| **写稿产物回流成参考库** | 每篇稿件按**内容硬性项**归入两区、按议题族供下次写稿调用——**产出即语料**（机制见 `docs/08`） |

> **这套动作的名字**：规则 → 用真实数据验证 → 发现漏洞 → 修订 → 再验证。
> 项目过程中这个循环跑了**三轮**，每一轮都改掉了一条真规则。

## 关于本仓库的数据

**本仓库只公开工作流，不公开任何真实数据。**

- 文档中的案例已**脱敏为代号**（如"某连锁药店旧闻新炒""某上市公司食品安全处罚"），
  规则、阈值、推理链、数据结构**完整保留**
- 不含任何真实稿件、内部台账、**工作单位与地域标识**
- 仓库内有脱敏自检脚本，**命中即拒绝发布**
