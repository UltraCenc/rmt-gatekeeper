## 二、★环境事实：沙箱下取数必须由 Harness 代跑★

**这是本次最花时间的一环，也是最该记下来的一环。**

原来设想"一个 Node 脚本自己调 ego-browser 抓完就出结论"，实测**在当前沙箱下不可能**，逐条排除如下：

| 尝试 | 结果 |
|---|---|
| `spawnSync` 默认管道捕获输出 | **EPERM**（沙箱把管道当命名管道拒掉） |
| `spawnSync(..., {input})` 喂 stdin | 挂住，`status: null` |
| `execSync` / `execFileSync` | **EPERM** |
| `cmd.exe /c "... < 文件"` 重定向 stdin | **Access is denied**（不能为子进程新建 stdin 句柄） |
| `stdio: ['ignore', fd, fd]` + 输出重定向到**文件** | ✅ **可行**（fd 不是管道） |
| `browser.openOrReuseTab()` 开独立标签页并发 | **EPERM**（要写 `%LOCALAPPDATA%\ego-lite-linux\task-spaces.json`） |

**结论（两条）：**
1. **取数脚本必须由 Harness 托管执行**（ego_script，或 shell 里 `Get-Content 文件 | node ego-browser.mjs`）；
   `scrape.cjs` 只负责**生成**脚本，不负责跑。
2. **worker 之间共享同一个 page 对象 → 必须串行**。曾用并发 3 跑 4 条候选，
   **其中 3 条的数据全串成了同一条**（A 的 `goto` 之后 B 又跳走，A 再取文本就是 B 的页面）。
   单条约 5.2 秒，16 条约 1.5 分钟，可接受。

## 四、★实测校准出来的五个坑（都是真数据打出来的）★

### 坑 1：并发共用 page 对象 → 数据串条
见第二节。修法：串行。

### 坑 2：法规施行日被当成发帖时间 → 算出"最新帖 -18.9 天前"
搜索页正文里有「**2026年11月1日**施行」，被 `\d{1,2}月\d{1,2}日` 这一型抓走当发帖时间。
**负的天数**还被当成"新"放行。

**修法（两道）：**
- 时间戳抽取分**两档**：A 档"发文格式"（必须带时刻：`30秒前`/`今天14:06`/`10月12日 10:00`）优先；
  B 档裸日期（`2026年11月1日`/`10月12日`）**只当 A 档一条都没有时的兜底**。
- `latestStamp` **一律剔除未来日期**（发帖时间不可能在未来），并单独记录到 `future` 字段备查。

### 坑 3：词条名必须与微博**逐字一致**
用简称"某养老陪伴服务议题养老陪伴服务"去查，两个入口都空——真名是"某养老陪伴服务议题"，一查就有数据。
**这会让"查不到"被误报成"议论不足 → 否决"。**

**修法**："查不到"分三种，结果各不相同：
| 情况 | 结果 | 为什么 |
|---|---|---|
| 页面明确提示"未找到" | `unknown_topic` | 词条名与微博不一致，须用榜单原词条名重查 |
| 无"未找到"字样、也无时间戳 | `need_data` | 疑取数异常（限流／改版），**不敢判** |
| 替代判据已算出 enough/thin | **按替代判据出结论** | ★不许被上面两条覆盖★ |

### 坑 4（回归）：护栏覆盖了已经算出来的结论
"女方回应被男方要求返还2万彩礼"（热度值 130 万、第 3 位）替代判据算出"议论偏薄"，
却被"词条名对不上"覆盖成"未判定"——**结论被丢了**。
修法：护栏的**前提**绑到"替代判据本来就不够格"上，而不是"没取到数据"。

### 坑 5：判定逻辑写错变量名
`judgeItem` 里 `discuss` 未定义（应为 `disc`）——**单元测试当场抓到**。
这条本身不算坑，记它是因为：**规则代码不写测试就等于没写**。

### 坑 6（★最严重的一个，会把结论系统性带偏★）：裸词条名＝模糊搜索，高估时效

入口乙原实现：`link 带 %23 → 用 #词条名#，否则用裸词条名`。
对**没有榜单原链**的候选，就走了**裸词条名**——那是**模糊全文搜索**。

**实测对照（词条：某养老陪伴服务议题）：**

| 抓法 | 捞回的时间戳 |
|---|---|
| 话题页 `topic?q=` | **一个都没有**（只有量：696 讨论／327.7 万阅读） |
| 搜索页 `#某养老陪伴服务议题#`（精确） | 09月11日 12:57、09月11日 11:50、08月12日 06:34、01月21日、10月16日 → **最新 9月11日** |
| 搜索页 `某养老陪伴服务议题`（裸名，模糊） | 今天10:41、1小时前、43分钟前、今天11:05、今天10:31… → **一堆今天** |

裸名搜索捞回的标签串是：`#北京街头出现某养老陪伴服务议题#`、`#年轻人自愿成为某养老陪伴服务议题#`、
`#宁波某养老陪伴服务议题为失独老人筹备新年团圆宴#`、`#大s遗产母亲和儿女共享系谣言#`——
**同族话题的帖子被当成了本词条的议论。**

**后果**：我据此判"某养老陪伴服务议题议论是新的、可写"，与用户 10-13 手工深翻的结论（`#某养老陪伴服务议题#` 话题页帖子仅 5 条、
最新 9月11日）**正好相反**。当时用户已定性"时效性不强，直接 pass"。

**修法**：入口乙**一律**用 `#词条名#` 精确检索。

**修后验证**：判定器输出 **最新帖 32.1 天前（09月11日 12:57）→ ✗ 否决（议论时效）**，
与用户手工记录**一字不差**。

> **这条的普适教训**：**没有榜单原链时，裸词条名搜出来的时间戳不能当"本词条的议论时效"**。
> 宁可出"数据不足"，也不要拿模糊搜索的结果下结论——它只会往"更新"的方向偏，
> 也就是**专门放过那些该被时效否决的题**。

### 坑 7（★★最严重★★）：整页 innerText 抽时间戳 = 把侧栏/推荐当成帖子

**症状**：`某养老陪伴服务议题` 判定在两次运行间摆动——"旧（32.1天前：09月11日）" ↔ "新（8分钟前）"。

**根因**：原来用 `page.evaluate(() => document.body.innerText)` 拿整页文本、再正则抽时间戳。
**搜索结果页的整页文本包含侧栏、相关话题推荐、热搜榜**——那些地方也有时间字样。

**定位过程（决定性证据）**：直接在 DOM 里查"8分钟前/1小时前"这类元素在不在帖子卡里——

```
page.evaluate: cards = 5（只有 5 个帖子卡）
  西安晚报   09月11日 12:57
  哏都养老院  09月11日 11:50
  尉迟笑盐团  08月12日 06:34
  风芒新闻   01月21日 17:57
  科技最前线  2025年10月16日 12:22
orphanTimeEls: []   ← ★页面上根本不存在"8分钟前"★
```

**修法**：议论时效**只用逐卡片抽出来的帖子时间戳**（`out.posts` → `out.stamps`）；
整页正则结果降级为 `out.pageStamps`，**仅供排查、绝不参与判定**。

**修后**：`某养老陪伴服务议题` 稳定输出 **最新帖 32.1 天前（09月11日 12:57）→ ✗ 否决**，
与用户 10-13 手工深翻记录**一字不差**。

> **教训升级**：上一版我把"裸词条名＝模糊搜索"当成根因，那是**次因**。真正的主因是
> **取数的位置错了**——不是帖子里的时间，就不该叫"议论时效"。
> 判断一个时间戳能不能用，标准只有一条：**它在不在帖子卡片里。**

### 坑 8：`s.weibo.com/topic?q=` 根本不是帖子列表

原以为话题页是"抓原话的帖子池"（手册 §三之二 1-bis 就是这么写的）。**实测不是**：

| 页面 | 实际是什么 |
|---|---|
| `s.weibo.com/topic?q=某养老陪伴服务议题` | **17 张"相关话题"卡**（每张是一个词条＋讨论量／阅读量），**零帖子** |
| `s.weibo.com/topic?q=某社保欠缴处罚新规` | 只有 1 张词条导航卡，**零帖子** |
| `s.weibo.com/weibo?q=%23词条%23&t=769` | **真正的帖子列表**（5～19 张帖子卡） |

**所以：**
- **"量"只能从 `topic?q=` 的词条卡读**（`696讨论 327.7万阅读`）——这点没错；
- **"帖子／时效／发帖人"只能从 `weibo?q=` 读**；
- **`topic?q=` 页面上读不到任何帖子时间戳**——这不是"抓不到"，是**那个页面本来就没有帖子**。

> ⚠ 还有一层坑：`topic?q=某养老陪伴服务议题` 返回的 17 张卡里，**第一张卡的讨论量恰好是 696／327.7万**，
> 但它属于 **`#北京街头出现某养老陪伴服务议题#`**，不是 `#某养老陪伴服务议题#`。
> **在本词条没有独立话题卡时，很容易把同族话题的量当成本词条的量。**
> 判定器现在的做法是：`topic?q=` 返回的第一张卡的量只在该页**恰好是本词条卡**时才采信，
> 否则按榜单词条型处理（本次 7 条候选里，"某低价商品仅退款争议"就是这样被正确降级的）。

### 坑 9：`page.evaluate(fn)` 看不到脚本作用域的变量

在 `page.evaluate` 的回调里调用 `__lib.parseStamp(...)` → **`ReferenceError: __lib is not defined`**。
原因：`page.evaluate(fn)` 是把 `fn` **序列化后送进页面执行**的，闭包变量带不过去。

**修法**：页面回调**只取原始 DOM 标识**（名字、vip img src、svg class、时间字样），
**解析与分类回 Node 侧做**（那里有 `__lib`）。

### 坑 10：模板字符串里的反引号（同一处踩了三次）

`page_scrape.gen.cjs` 用模板字符串生成脚本。**在模板字符串内部的注释或字符串里写反引号，
会把模板提前闭合，导致生成器本身语法错误**——而且报错位置指向注释，很容易误判。
`${` 同理（会被当插值）。

**三次记录**：注释里写 `` `#词条名#` `` → 注释里写 `` `pageStamps` `` → 错误信息里用模板字符串。
**修法**：生成器里**改字符类不用 `\d`**（写 `[0-9]`），**注释里不用反引号**，
并在 `check_generated.cjs` 加**自动护栏**：生成结果含反引号或 `${` 即判失败。

## 七、★闸门 3-②：发帖人构成抽样（交接文件 4.2-B，已完成）★

**要堵的漏**：帖子密度**只看时间、不看是谁发的**。"某社保税务处罚口径"新鲜帖 100%，
但发帖主体是财经博主解读——密度判据放它过关。

**识别办法（实测 DOM）**：

| 页面标识 | 判为 |
|---|---|

### ★由此发现并修掉的一个判据漏洞★

第一版判据只有一条线：`普通用户（含月费会员）占比 ≥30%`。
**"某婚宴纠纷"能钻过去**——蓝V 7 条、普通 0 条，但 6 条"月费会员"被计入普通用户后，

**修法：加第二条线**——`达人/机构（蓝V＋黄V）占比 ≥50%` 同样判为主导。

实测 `某社保税务处罚口径`：24h 新帖 12 条里 **会员 11 条／普通 1 条**，

**为什么不能简单修**：微博活跃用户里**大部分都带会员标识**，
若把"会员"一律排除出"普通用户"，剩余样本会趋近于零，判据直接失效。
